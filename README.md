# mcc

一个从头写的我的世界服务端，把原版 1.21.1、机械动力（Create）和 Sable 物理做成一个程序，不需要模组加载器。

- 服务端用 C++23 写，物理引擎是改造过的 Box3D（C）。
- 按 Folia 的方式把世界分成区域，多线程同时跑 tick。
- 物理直接读世界的区块数据，方块只存一份。

目前还不能用正版客户端进游戏：网络协议、玩家、存档都还没做。现在用自带的测试客户端看效果。

> **以后要删掉重写：** `src/game/`，以及机械动力里依赖原版的部分。
>
> 1. 用 NeoForge 的 gradle 初始化反编译出 Minecraft 1.21.1 的原版源码；
> 2. 照原版源码逐个类重写 `src/game/`，每处注明对应原版的哪个文件；
> 3. 机械动力里依赖原版的部分在新的 `src/game/` 上重新移植。

---

## 目标

1. **性能和多线程第一。** 原版和模组里为了兼容旧架构做的绕路写法都不照搬，用更直接、更快的方式实现。
2. **功能不改。** 机械动力、原版的行为照原版来；要改哪里由项目负责人决定。原版的 bug 改不改，也由负责人定。
3. **原生实现，不打补丁。** 机械动力和 Sable 在 NeoForge 上靠"修改原版"实现的功能（比如风扇吹船、帆产生升力），在这里直接写进服务端本身。

---

## 现在能做什么

- **物理**：方块结构（子世界）落地、碰撞、堆叠、在水里漂浮，远离原点（几千万格）也不丢精度。地形和结构都直接读区块存储，改一个方块，物理马上生效。
- **区域多线程**：区域的合并、拆分，以及区域之间搬运区块、物理结构、方块实体、计划刻，都有多线程测试覆盖。
- **机械动力的动力网络**：转速传递、应力和容量、网络合并拆分、超速破坏、转向冲突破坏，照机械动力源码移植。已有的方块：
  - 传动杆、齿轮、大齿轮；
  - 安山岩和黄铜机壳传动杆、机壳齿轮；
  - 齿轮箱、离合器、换向器；
  - 链式传动、可调链式变速箱；
  - 创造马达、转速控制器。
- **测试客户端**：原生程序（Windows / Linux）。可以走、跳、飞，放置和拆除方块，看零件转动，用物理枪拖结构，扔炸弹炸结构。

  world/     方块注册表、区块存储、"维度"（把区域、区块、物理接在一起）

  game/      游戏逻辑底层：放方块、方块更新、计划刻、方块实体；还没做的系统的留空接口
  create/    机械动力
    kinetics/  动力网络和动力零件
  debug/     调试服务端：生成测试场景，和测试客户端通信
  client/    测试客户端（raylib）

data/        方块、碰撞形状、物理属性等数据（原版和机械动力分文件）

## 编译和运行

需要 CMake 3.20 以上，以及支持 C++23 的 GCC。

**Linux**

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
ninja -C build
./build/mcc_client        # 测试客户端，会自动启动同目录下的 mcc_debug
```

客户端需要 X11 和 OpenGL 的开发包（Debian/Ubuntu：`libx11-dev libxrandr-dev libxinerama-dev libxcursor-dev libxi-dev libgl-dev`）。

**交叉编译 Windows 版**（需要 mingw-w64 的 posix 线程版）

```sh
cmake -S . -B build-win -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-w64.cmake \
      -DMCC_ARCH="-march=x86-64-v3 -mtune=znver4"
ninja -C build-win mcc_client mcc_debug
```

Windows 版是静态链接的，只依赖系统自带的 DLL。发给别人时，把 `mcc_client.exe`、`mcc_debug.exe` 和 `data/` 放在同一个目录里。

**编译选项**

| 选项 | 默认 | 说明 |
|---|---|---|
| `MCC_ARCH` | `-march=native` | 目标 CPU 指令集。发给别人的包要改成通用的，比如 `-march=x86-64-v3` |
| `MCC_CLIENT` | `ON` | 是否编译测试客户端 |
| `MCC_TSAN` | `OFF` | 用线程竞争检测器编译（查多线程 bug） |
| `MCC_ASAN` | `OFF` | 用内存错误检测器编译 |

**调试服务端**

```
mcc_debug [端口=8080] [跑 tick 的线程数=2] [帮手线程数=核数-跑 tick 的线程数]
```

启动后会生成一个室内大厅当测试场景，出生点前面摆着一套机械动力演示机器。

**测试**

```sh
./build/test_phys              # 物理：落地、堆叠、漂浮、远离原点的精度
./build/test_create_kinetics   # 机械动力：转速传递、冲突、区域合并拆分时的动力网络
./build/test_level             # 多线程下区域合并拆分，物理结构跟着搬
./build/test_regionizer        # 区域划分和 tick 调度的多线程压力测试
./build/test_world             # 区块存储
./build/test_boxbox            # 长方体碰撞，和 Box3D 自带算法对比结果和速度
./build/test_region_fuzz       # 区域划分随机测试（较慢）
./build/test_phys_bench 4 2000 200   # 物理性能：4 个帮手线程、2000 个结构、200 刻
```

## 测试客户端

双击 `mcc_client.exe`（Linux 上是 `mcc_client`）就行。连不上本机服务端时，它会自动启动同目录下的 `mcc_debug`，关客户端时一起关掉。连别的机器：`mcc_client 地址 端口`。

| 操作 | 按键 |
|---|---|
| 移动、跳、跑、潜行 | WASD、空格、Ctrl、Shift |

| 选物品 | 1~0 或滚轮，Tab 切换第二页 |
| 拆 / 放 | 左键 / 右键（Shift+右键：马达反向放） |
| 调马达、转速控制器的转速 | 看着它按 `[` `]`，每次 ±8 RPM，停手半秒后一次生效 |
| 物理枪（第 1 格） | 按住左键抓结构，滚轮调远近，松开扔出去；抓着时右键冻结，对冻结的结构右键解冻 |

## 多线程是怎么跑的

先说清楚几个词：
- **tick**：服务器每秒算 20 次，每次叫一刻。
- **区域**：和 Folia 一样，连在一起的已加载区块算一个区域，离得远的地方是不同的区域。
- **线程**：CPU 上干活的"工人"。

### 1. 区域之间：几个线程轮流给区域跑 tick

举例：一个世界里有 10 个区域，服务器开了 4 个跑 tick 的线程。

- 10 个区域按"下一次该 tick 的时间"排队。
- 哪个线程空了，就拿队里最早到点的那个区域，跑它这一刻；跑完把它按下一次的时间排回去，再去拿下一个。
- 同一个区域同一时间只会被一个线程跑，所以区域内部的数据不会被两个线程同时改。
- 一个区域卡了，只有它自己慢，别的区域照常。短时间落后会连着补跑几刻追回来，落后超过 1 秒就放弃追赶。

和 Folia 不同的是，区域合并、拆分时，除了区块，还要把物理结构、方块实体、计划刻、机械动力的动力网络一起搬过去；两个区域的刻数不一样，计划刻的时间要换算。

### 2. 区域之间怎么沟通

不能直接去改别的区域。比如客户端要在某处放方块，就给那个位置所在的区域"留一张便条"（任务），那个区域下一刻开头先把便条上的事办掉。

"哪个区块归哪个区域"这张表，任何线程随时都能直接查，不用排队；只有区域合并、拆分改表时才一个一个来。改表时旧记录不马上删，等所有可能正在查它的线程都查完了再删。

### 3. 区域内部：一刻里按什么顺序做事

1. 执行别的地方留过来的便条；
2. 游戏逻辑：计划刻、方块实体（包括机械动力零件）、方块更新；
3. 物理；
4. 把变化同步给客户端。

### 4. 帮手线程

另有一批全服共用的帮手线程。一个区域某一步的活特别大时（比如几千个结构互相碰撞），可以拆成很多小份交给帮手一起算，区域自己的线程也一起干。帮手自己的活干完了，会去别的帮手那里拿活，不会有人闲着。

所以一个物理很重的区域能同时用好几个核，这是 Folia 没有的。

**现在的限制：**
- 帮手只用在物理上。游戏逻辑（第 2 步）还是区域线程自己一个人按顺序算。
- 物理是按"一对互相接触的物体"分活的。很多结构时能分给很多线程；但一个大结构（比如几百上千格的飞船）压在地面上只算一对（地形按 256×256 格一块划分，飞船通常只落在一块上），两艘大船互撞也只是一对，这一对的碰撞只由一个线程算。

两条都在下面的待办里。

## 物理

- 每个有物理结构的区域有一个物理场景；物理结构在区域之间迁移时，刚体在新场景里重建。
- 物理结构的方块存在很远的"地块"区域里（沿用 Sable 的 2000 万格偏移），因为不影响性能，所以保留。
- 方块碰撞按 parry 的思路优化：一整片整格方块合成大板来碰，结构内部被包住的方块不算。
- 高速运动时（一步靠近超过 0.4 格）按速度提前生成接触，防止穿过地面和墙。
- 重力是原版物理默认值的 3×2.76 倍（`src/debug/main.cpp`）。

## 机械动力

- 照机械动力源码（`ref/create`，例如 `RotationPropagator.java`、`KineticBlockEntity.java`）移植，原版的递归改成了显式栈，避免调用层数太深导致崩溃。
- 动力网络按空间分开存，没变化时零件不 tick。
- 修了原版的三个 bug，代码里有说明：移除零件后动力来源没清干净；清除动力信息后零件还留在网络里；递归过深导致栈溢出。
- 保留了原版的"转速抖动保护"：短时间内同一条传动线停转、反转次数太多，会把零件拆掉（原版 `RotationPropagator` 里的 `MAX_FLICKER_SCORE`）。

## 约定

- 服务端代码用 C++23，Box3D 保持 C。编译时关掉异常和运行时类型信息。
- 只在 `master` 分支上开发。
- 需要用到但还没做的系统（红石、掉落物、网络、存档、流体、玩家交互、物理结构接入），一律在 `src/game/pending.h` 里留一个现在什么都不做的接口，调用位置和时机照原版。搜索 `TODO(` 能找全。
- 火车和动态结构以后改成我们自己的原生物理结构，现在只留接入点，不移植机械动力原来的移动代码。
- 区域里的代码（机器、物理、怪物）不直接改玩家的状态，一律通过任务传过去（为以后的玩家专用线程做准备）。
- 每个区域的状态要能完整打包，不依赖全局共享的可变数据（为以后多台机器一起跑做准备）。
